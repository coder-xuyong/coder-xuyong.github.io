## 数字网格项目

### 隐患排查
#### 侧重业务
- 设计并实现隐患全生命周期状态机（待整改 / 超时待整改 / 已整改待确认 / 已确认 / 撤回 / 驳回 共 8 种状态），覆盖从提交、整改、确认到驳回复核的完整闭环；
- 基于 XXL-Job 实现超时自动判定定时任务，批量扫描超过整改时限的待整改记录并自动流转状态，保障超时逻辑的准确性与时效性；
- 使用 MyBatis-Plus LambdaQueryWrapper 构建多条件动态查询，配合批量查询优化（一次 selectByIds 填充关联用户名），避免 N+1 问题；
- 基于 Spring Cloud Gateway + Nacos 实现微服务网关路由与统一鉴权，JWT 令牌校验 + 白名单放行机制。

#### 侧重「性能 & 质量」
- 负责隐患模块后端核心逻辑开发，包括隐患提交、整改、确认、撤回、驳回及超时自动流转；
- 针对列表查询中的 N+1 问题，采用批量 ID 查询 + HashMap 映射的方式将用户名称一次性填充，查询次数从 O(n) 降为 O(1)；
- 设计「待整改 → 超时待整改」的定时批量处理机制，单次 SQL 更新完成状态流转，避免逐条查询更新；
- 全局统一异常处理，规范返回 {code, msg} 错误码，前端可统一解析。

### 记录一次排查
rectify接口修改之后，返回列表界面调用了list，返回的状态正常；但是进去详情再返回，状态又变回了初始状态，这是为什么？

getDetail 本身不会修改状态，问题出在 rectify 与 handleInstanceId 之间的异步竞态条件：
```text
rectify (@Transactional)                              handleInstanceId (RabbitMQ 异步)
1. selectById → status=1（旧值）
2. setStatus(5)          ← 只改内存
3. startProcess() → 发 RabbitMQ ———————→ 4. selectById → status=1
                                                          （rectify 事务还没提交！）
5. updateById → status=5（未提交）
6. 事务提交 → status=5 生效
7. updateById → status=1
    （自动提交，覆盖了 5！）
```

## 📊 自定义代码 vs FlowLong 框架代码分析

### FlowLong 框架提供了什么（底层引擎）

FlowLong 是一个开源工作流引擎，它提供了：
- 流程定义、实例、任务、参与者等核心实体
- 流程启动、流转、审批、驳回、撤回等基础 API
- 任务监听器、参与者提供者、访问策略等 **SPI 扩展点**（接口）

## 🎯 结论：**建议写进简历，但要换个角度**

这个项目的价值不在于"用了 FlowLong"，而在于：

1. **基于开源引擎做深度二次开发** — 你是在框架的 SPI 扩展点上做了大量定制，不是简单调 API
2. **事件驱动架构设计** — 用 RabbitMQ 8 个队列解耦流程各环节，含分布式锁、幂等性设计
3. **复杂业务建模** — 多维度审批人分配（角色/部门/指定人）、动态路由跳转、条件分支
4. **多数据源整合** — MySQL + MongoDB + Redis + Caffeine 各司其职
